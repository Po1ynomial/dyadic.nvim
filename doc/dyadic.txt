1. INTRODUCTION                                                 *dyadic-intro*

dyadic.nvim talks to pi (https://pi.dev) through pi's RPC mode
(`pi --mode rpc`), and loads a small pi extension of its own, the bridge
(|dyadic-bridge|), for what stock RPC lacks. An agent is one pi process with
two buffers: the read-only history, which shows the messages of pi's current
session, and the composer, where you write the next message with normal
Neovim editing. There is no embedded terminal and no required UI library.

Requirements:
- Neovim 0.11 or newer.
- `pi` on $PATH, with provider authentication and pi configuration set up.
  The bridge needs pi 1.5.2 or newer.

==============================================================================
2. SETUP                                                        *dyadic-setup*

Setup is optional. Defaults:
>lua
    require("dyadic").setup({
      cmd = { "pi" },
      args = {},
      bridge = true,
      placement = "sidebar",
      sidebar = {
        side = "right",
        width = 0.35,
        min_width = 40,
        max_width = 120,
      },
      composer = { min_height = 3, max_height = 0.4 },
      statusline = true,
      completion = true,
      mappings = {},
      double_escape = "tree",
      tree = { keys = {} },
      sessions = { keys = {} },
      review = false,
      change_notes = false,
    })
<
`cmd`           Executable argv array. dyadic appends `--mode rpc`; do not
                pass another CLI mode.
`args`          Pi arguments that go before every agent's, like a shell
                alias, such as `--model` or `--session-dir`. The arguments
                |:Dyadic| refuses are refused here too, and so are
                messages. Pi still loads its own configuration, tools,
                extensions, skills, and templates.
`bridge`        Load dyadic's pi extension (|dyadic-bridge|). With `false`,
                pi runs stock and the features that need the bridge are
                unavailable.
`placement`     Where the pair goes: `"sidebar"` or `"free"`
                (see |dyadic-windows|).
`sidebar`       Side of the tab, starting width as a share of the editor,
                and its limits in columns.
`composer`      Limits of the composer's height in lines. A `max_height`
                below 1 is a share of the space the history and composer
                share.
`statusline`    Show which buffer a window holds and pi's session ID in the
                statusline of dyadic's windows. Set to `false` to keep yours.
`completion`    Complete commands and paths in the composer, through its
                'omnifunc' and a blink.cmp source (see
                |dyadic-completion|). `false` turns both off.
`mappings`      Override or disable default keys (see |dyadic-mappings|).
`double_escape` What <Esc><Esc> does while idle: `"tree"`, `"fork"`, or
                `"none"` (see |dyadic-double-escape|).
`tree`          Tree picker keys (see |dyadic-tree|).
`sessions`      Session picker keys (see |dyadic-sessions|).
`review`        Which files' changes you review before they land, and the
                review keys (see |dyadic-review|).
`change_notes`  Tell the agent when files it has seen change (see
                |dyadic-change-notes|).

Configuration applies to agents opened afterwards. Each agent captures
Neovim's effective cwd when it opens, including window- or tab-local cwd,
and keeps it after later |:cd| commands.

Pi's environment is Neovim's, except that an inherited `$NVIM` or
`$NVIM_LISTEN_ADDRESS` is removed. Neovim sets `$NVIM` only for |jobstart()|
and |terminal| children, so an inherited value names an outer Neovim.

3. AGENTS                                                      *dyadic-agents*

`:Dyadic` shows the agent you used last, or opens one, and goes into its
windows (|dyadic-focus|). `:Dyadic new` opens another agent and pi process,
and `:Dyadic -c`, `:Dyadic -r`, or any other pi arguments open one as `pi`
would with them (|dyadic-pi-arguments|). An agent shows one pi session at a
time; `/new` and `/resume` change the session without changing the agent.
Pi runs a session in the directory it was created in, so the agent's
working directory follows a resumed session; paths in the history and the
composer resolve against it.

The history and composer are unlisted scratch buffers named
`dyadic://<id>/history` and `dyadic://<id>/composer`. Hiding them does not
interrupt the agent. Running `:Dyadic close`, or unloading either buffer
with |:bdelete|, |:bunload|, or |:bwipeout| (also as `:%bd`), ends the
agent's process and disposes its buffers, details, and pending extension
dialogs. |:edit| in either buffer only reloads it: the history is written
again and the composer keeps the draft. Closing an agent never deletes its
session file.

Quit guard                                                *dyadic-quit-guard*
While any agent streams, compacts, retries, or runs a shell command, quitting
Neovim is refused like quitting with unsaved changes: |:q|, |:qa|, and |:wqa|
fail with E37 or E162, and a :q that would exit explains why. |:qa!| still
quits and ends every pi process dyadic started. The guard is a hidden
buffer, `dyadic://agent-working`, that stays modified while work is in
progress.

Notices go through |vim.notify()|. Pi's stderr goes to a temporary log file
instead; if pi exits unexpectedly, one notification gives the exit code and
the log's path.

4. WINDOWS                                                    *dyadic-windows*

The history window and the composer, a split directly below it, form a
pair: neither shows without the other. An agent has at most one pair in each
tab, and pairs in different tabs show the same draft.

The pair stays together:
- The composer's height follows its content (draft, widgets, and footer)
  within `composer.min_height` and `composer.max_height`; resizing it by
  hand is undone.
- A composer moved elsewhere, for example with CTRL-W K, is put back.
- Closing either window closes both. When they are all the tab has, |:q|
  closes the tab or quits Neovim, and |:close| leaves them open.
- |:only| in either window keeps both.
- A split of either window, such as |:vsplit| in the history, is undone.
  Other windows split inside the pair, such as |:new|, move out beside the
  window you last used outside it.
- The composer refuses other buffers (|dyadic-own-windows|). Showing
  another buffer in the history window closes the composer; the draft is
  kept.
- Showing the history or composer buffer in another window, as with
  |:buffer|, moves the tab's pair to that window with the free placement.
  With the sidebar, the window gets its buffer back and the sidebar shows
  the agent.

                                                            *dyadic-focus*
`:Dyadic` and `:Dyadic toggle` go into the pair at the window of it you used
last, else the history, in Normal mode. From inside the pair, `:Dyadic
toggle` hides it and goes back to the window you used last outside it, so
one mapping moves between your code and the agent:
>lua
    vim.keymap.set("n", "<C-.>", "<Cmd>Dyadic toggle<CR>")
<
                                                        *dyadic-own-windows*
The sidebar, the composer, and dyadic's floats (the tree picker, the
detail, the extension editor) show only their own buffers. They set
'winfixbuf', so |:bnext|, |[b|, |CTRL-^|, |:edit|, and the like fail there
with |E1513|. A forced switch, such as `:bnext!` or `:buffer! 3`, opens that
buffer in the main area instead: the sidebar and the composer get their
buffer back, and a float closes.

Placements                                                *dyadic-placement*
`"sidebar"` (default): each tab can have one sidebar, a column at the edge of
the tab with one agent's history and its composer.
- Showing another agent swaps it into the same windows. The previous agent
  keeps running and keeps its draft.
- The width starts at `sidebar.width` of the editor within `min_width` and
  `max_width`, and leaves the main area at least 40 columns. A manual resize
  is remembered as a share of the editor and applied again when the editor
  is resized. CTRL-W = leaves the sidebar alone.
- The sidebar window refuses other buffers (|dyadic-own-windows|). `gf`,
  `gF`, and CTRL-W f open files in the main area, resolving relative paths
  against pi's working directory. Windows split inside the sidebar move to
  the main area.
- |:q| on the last window outside the sidebar closes the sidebar too, so the
  tab closes or Neovim exits. When the quit is refused, the sidebar comes
  back.
- The sidebar never stands alone: when the main area's last window closes
  any other way, such as |:close| or |CTRL-W_o| in the sidebar, a new one
  opens across from it with the file you used last.

`"free"`: `:Dyadic` shows the agent's pair of the tab, or turns the current
window into it.
- Hiding the pair gives that window back the buffer it showed before, with
  its window options. A window opened for the pair, as from a float,
  closes, or shows the file you used last when the tab has nothing else.

5. HISTORY                                                    *dyadic-history*

The history buffer contains only message text, so it is plain markdown.
Everything else is overlay text drawn on empty lines, and every block has
one blank line around it:

  `▍ You`                       A speaker row; for the assistant, the model
  `▍ Assistant   model · 1m 5s` and the run's time are right-aligned
  `▎ ▸ thinking · 2 tools`       A collapsed group of activities
  `▎ ▾ 2 tools`                  An expanded group, one line per activity:
  `▎   ◦ bash make · done 1.2s`
  `▌ $ ls · exit 0`              A shell command run with `!` or `!!`
  `◇ Context compacted`          A compaction
  `↳ Branch summary`             A branch summary
  `usage · ...`                  Usage billed outside messages
  `✗ ...`                        An error or abort
  `⧗ steer · ...`                Queued messages, pinned to the end
                               until pi takes them

A run is one user message and all of the agent's work in reply. Its time
counts up while it is live; afterwards it runs to when pi saved the run's
last entry. A tool's duration shows only when pi reported it live.

Groups                                                      *dyadic-groups*
Consecutive tool calls and thinking blocks form a group. Once agent text
follows a group, it collapses. A group at the end of a run stays expanded
while pi works on it, and after the run was aborted or failed. History loaded
from a saved session starts collapsed.

`za` toggles the group under the cursor. `K` expands a collapsed group,
opens the detail of an activity or other row, and keeps its native behavior
elsewhere. `g]` / `g[` jump between speakers.

Detail                                                       *dyadic-detail*
`K` opens the full content of an activity, shell command, summary, or error
in a float over most of the editor. Its title is the tool, its status, and
its duration; other header lines, such as the command or path, stay above
the content. The content has a fitting filetype: the file's type for `read`
and `write`, `diff` for `edit` diffs, `markdown` for thinking and summaries.
The detail keeps updating while it is open, so it is where a running
command's output appears.

`q`, <Esc>, and `K` close the detail, and so does leaving it. `gf`, `gF`, and
CTRL-W f open files in the main area and close the detail.

Following output
A history window follows new output only while its cursor is on the last
line. Move the cursor up to read earlier messages without being moved. The
detail follows the same rule.

Filetypes
The history and composer use the filetypes `dyadic` and `dyadic_composer`,
so markdown ftplugins, LSP servers, and linters do not attach. Both are
registered as markdown for treesitter. To use a markdown rendering plugin,
add `dyadic` to its filetype list.

History follows pi's active branch and compaction boundaries: the latest
compaction's summary, then the entries it kept, then later entries. It
shows raw session entries, not model-only `context_edit` replacements, and
not the system prompt or extension messages marked hidden.

==============================================================================
6. COMPOSER                                                  *dyadic-composer*

The composer holds the draft, the unsent text, plus status around it:

- Its window bar shows a spinner and the agent's phase while it works, or
  `ready`, with the numbers of queued steer, follow-up, and after-compaction
  messages on the right.
- Below the draft come extension widgets placed below the editor, then the
  footer:
    `ctx 45%/200k (auto) · $0.123`   Context use, auto-compaction, cost
    `model · high`                   Model, and thinking level for models
                                   that reason
    `extension statuses`
  The percentage is `?` while pi reports none, as right after a compaction,
  and turns to warning and error colors above 70% and 90%. A zero cost is
  hidden.
- Extension widgets placed above the editor come before the draft.

The history window's bar shows the session title, with pi's working
directory on the right. With `statusline` on, the statusline of both windows
names the buffer and pi's session ID.

7. MAPPINGS                                                  *dyadic-mappings*

Defaults are buffer-local Normal-mode mappings. Insert and Visual mode keep
native Neovim keys. `:nmap <buffer>` lists the active set with descriptions.

Composer:

  Key               Action             Behavior ~
  <CR>              `submit`             Submit; steer while pi is working
  <M-CR>            `follow_up`          Submit as a follow-up
  <Esc>             `abort`              Return queued input, then abort
                                       (|dyadic-double-escape|)
  <M-Up>            `dequeue`            Return queued input to the draft
  <C-l>             `model`              Select a model
  <S-Tab>           `cycle_thinking`     Cycle thinking level

History:

  Key               Action             Behavior ~
  za                `toggle_group`       Expand or collapse a group
  K                 `detail`             Open the row's detail, or expand
  g]                `next_message`       Next speaker
  g[                `prev_message`       Previous speaker
  gf                `goto_file`          In the sidebar: open in the main area
  gF                `goto_file_line`     Same, at the line number
  <C-w>f            `split_file`         Same, in a split
  i                 `insert`             Insert in the composer's draft at
                                       its cursor
  a                 `append`             Same, after its cursor
  I                 `insert_start`       Same, at the start of the draft
  A                 `append_end`         Same, at the end of the draft
  o                 `open_below`         Same, on a new line after it
  O                 `open_above`         Same, on a new line before it

The history is read-only, so these keys take the place of Vim's own. With
an empty draft, each one just starts Insert mode. CTRL-W j and CTRL-W k move
between the history and the composer, which always sits right below it.

Actions without a default key: `thinking`, `cycle_model`, `copy`,
`settings`, `new`, `resume`, `tree`, `fork`. Every action has a buffer-local
<Plug> mapping named after it, for example `<Plug>(DyadicSubmit)`,
`<Plug>(DyadicToggleGroup)`, `<Plug>(DyadicCopy)`.

Override or disable defaults by action name:
>lua
    require("dyadic").setup({
      mappings = {
        submit = "<leader><CR>",
        model = false,
        copy = "<localleader>y",
      },
    })
<
                                                       *dyadic-double-escape*
As in pi, pressing <Esc> twice in Normal mode while the agent is idle runs
the `double_escape` action: `"tree"` (the default) opens the tree picker,
`"fork"` the fork picker, and `"none"` turns this off. In the composer it
runs only with an empty draft. The maps follow the agent: while it works, a
single <Esc> in the composer aborts and <Esc><Esc> does nothing; while it is
idle, <Esc><Esc> is mapped and a single <Esc> waits 'timeoutlen' for the
second. With `double_escape = "none"`, <Esc> always aborts.

Critical native keys such as CTRL-O, CTRL-T, CTRL-D, CTRL-W, and CTRL-X are
not replaced. Terminal support for modified Enter and Tab varies; remap those
actions when needed.

                                                           *dyadic-completion*
The composer completes in two places:

- A slash command on the draft's first line, where pi reads commands (see
  |dyadic-pi-commands|), and the arguments of `/settings`, `/thinking`, and
  `/model`. Built-in commands come before pi's extension, prompt, and skill
  commands, each with its description.
- A path after `@` at the start of a word, matched fuzzily against every
  file and directory below the agent's cwd: `@view` finds
  `lua/dyadic/view.lua`. The list comes from `fd`, or `rg --files` (files
  only), or Neovim walking the directory. With `fd` or `rg` it skips what
  `.gitignore` ignores; it includes hidden files but never `.git`. It is
  taken once per Insert mode, so leave Insert mode to see new files. A path
  with spaces is inserted quoted, `@"my file.md"`.

Nothing else completes: plain words and bare paths are prose. Nothing from
your buffers is attached to a prompt unless you type it.

With blink.cmp installed, dyadic adds its source for composers the first
time one enters Insert mode; nothing needs configuring. Typing `/` or `@`
opens the menu. Accepting `/model`, `/thinking`, `/settings`, or a setting
name opens its arguments. The documentation window shows what a command
does, a model's context window, output limit, reasoning, and image input,
and the start of a file. To place the source yourself, configure it under
any name; dyadic then uses that one: >lua
    sources = {
      providers = {
        dyadic = { name = "Dyadic", module = "dyadic.completion.blink" },
      },
    }
<
Do not also enable blink.cmp's `omni` source for `dyadic_composer`: it
would list every item twice.
Without blink.cmp, |i_CTRL-X_CTRL-O| completes the same places, with the
descriptions in the menu and the preview. `/model` arguments need a request
to pi, so only blink.cmp completes them, and `/thinking` offers the levels
pi reported the last time they were asked for. Other completion plugins
with an omnifunc source, such as cmp-omni, use the 'omnifunc' too.

8. PI COMMANDS                                            *dyadic-pi-commands*

Type these in the composer and submit:

  `/model [provider/model or search]`  Select a model
  `/thinking [level]`                  Select a supported thinking level
  `/new`                               Start a fresh session in this agent
  `/resume`                            Switch to a saved session with the
                                     session picker (|dyadic-sessions|)
  `/name [name]`                       Set or show the session name
  `/session`                           Show identity, file, usage, context
  `/compact [instructions]`            Compact through pi
  `/tree`                              Move within the session tree with
                                     the tree picker (bridge, see
                                     |dyadic-tree|)
  `/fork [entry-id]`                   Fork from a user message and restore
                                     its text to the draft
  `/clone`                             Clone the active branch
  `/export [HTML path]`                Export HTML through pi
  `/copy`                              Copy the last assistant response
  `/settings [name] [value]`           Auto-compaction, auto-retry, steering
                                     mode, or follow-up mode
  `/reload`                            Reload pi's extensions, skills,
                                     prompts, and context files (bridge)
  `/quit`                              Close this agent
  `!command`                           Run a shell command; its output joins
                                     pi's context
  `!!command`                          Run a shell command; its output stays
                                     out of model context

Settings change the active pi session, not your settings files.

Extension commands, skills, and templates from pi's `get_commands` are
forwarded to pi. Input submitted during compaction is queued locally and sent
when compaction finishes. Abort returns pi's queues and that local queue to
the draft without discarding newer unsent text.

TUI-only commands are rejected locally instead of becoming prompts: login
and logout, scoped models, share and bug workflows, trust management, and
`/hotkeys` (use `:nmap <buffer>`). A name pi lists as an extension command,
such as `/llama`, is forwarded instead.

Tree picker                                                     *dyadic-tree*

`/tree`, `:Dyadic tree`, the `tree` action, or <Esc><Esc> while idle
(|dyadic-double-escape|) open a float with the session's tree of entries, as
pi's own `/tree` shows it: the active branch is marked `•`, labels show in
brackets, and branches hang off `├─` and `└─`. Opened from the history, the
cursor starts on the entry under the history's cursor, otherwise on the
current entry. It needs the bridge and an idle agent.

Each row is one entry; the cursor line is the selection, so Neovim's motions,
scrolling, and folds work as usual. Keys in the list:

  Key       Name                        Action ~
  <CR>      `navigate`                    Go to the entry, asking whether to
                                        summarize the branch you leave
  <C-CR>    `navigate_without_summary`    Go to the entry without a summary
  /         `search`                      Focus the search bar
  <Esc>     `cancel`                      Clear the search, else close
  q         `close`                       Close
  h         `fold_or_up`                  Fold the row, else go to the
                                        previous branch segment
  l         `unfold_or_down`              Unfold the row, else go to the
                                        next branch segment
  d         `filter_default`              Default view
  t         `filter_no_tools`             Toggle: no tool results
  u         `filter_user_only`            Toggle: your messages only
  '         `filter_labeled_only`         Toggle: labeled entries only
  a         `filter_all`                  Toggle: every entry
  <Tab>     `filter_next`                 Next filter
  <S-Tab>   `filter_prev`                 Previous filter
  m         `label`                       Set or clear the entry's label
  T         `label_time`                  Show or hide label times
  yy        `copy`                        Copy the entry's full text to
                                        |v:register|

Change or disable them with `tree.keys`:
>lua
    require("dyadic").setup({
      tree = { keys = { label = "L", copy = false } },
    })
<
Typing in the search bar filters the list at once; every word must match.
There, <CR> and <C-CR> go to the selected entry, <C-n>, <C-p>, <Down>, and
<Up> move the selection, and <Esc> returns to the list with the search kept.
A root or the first entry of a branch can fold; folds are Neovim's manual
folds, so |za|, |zo|, |zc|, |zR|, and |zM| work too. Changing the filter or
the search opens all folds, as in pi. <C-CR> reaches Neovim only in
terminals that send modified keys, such as kitty, Ghostty, WezTerm, foot,
and tmux with `extended-keys`.

Going to an entry asks whether to summarize the branch you leave: no
summary, a summary, or a summary with instructions you type. While pi
summarizes, the composer shows `summarizing branch` and <Esc> there cancels,
which returns to the picker. Going to one of your messages moves to the
entry before it and adds its text to the draft; any other entry becomes the
current one. Leaving the picker's windows closes it.

Session picker                                              *dyadic-sessions*

`/resume`, the `resume` action, and `:Dyadic -r` open a float with pi's
saved sessions, as pi's own session selector lists them. From `/resume`,
the session you choose replaces the agent's; from `:Dyadic -r`, it opens in
another agent. It does not need the bridge.

The list starts with the sessions of the agent's directory, or of Neovim's
cwd for `:Dyadic -r`, with forks under the session they came from. Each row
shows the session's name, else its first message, then its message count
and how long ago it was last active. Named sessions stand out, `•` marks
the agent's own session, and `agent 2` marks one a live agent shows. The
All view groups every directory's sessions under a row for the directory;
the current one comes first and open, the others folded. Sorted by recency
or relevance, the rows are flat, and in the All view show their directory.

The preview beside the list, or below it in editors narrower than 120
columns, shows the session under the cursor: its full name and first
message, the last message and reply, and its directory, model, thinking
level, message count, times, ID, file, and the session it was forked from.

Keys in the list:

  Key       Name               Action ~
  <CR>      `open`               Open the session; on a directory, fold or
                               unfold it
  /         `search`             Focus the search bar
  <Esc>     `cancel`             Clear the search, else close
  q         `close`              Close
  h         `fold_or_up`         Fold the row, else go to its parent
  l         `unfold_or_down`     Unfold the row, else go to its first child
  <Tab>     `scope`              This directory or All, also while typing
  s         `sort`               Threaded, recent, or relevance
  n         `named`              Toggle: named sessions only
  p         `preview`            Hide or show the preview
  dd        `delete`             Delete the session after |confirm()|
  yy        `copy`               Copy the session file's path to
                               |v:register|

Change or disable them with `sessions.keys`, as with `tree.keys`.

Typing in the search bar filters at once on names, first messages, IDs, and
directories; every word must match. After a pause, dyadic also searches the
message text of the other sessions in the background, with `searching` in
the title, and adds those that match. With a search, the threaded sort lists
by relevance, as in pi: matches in the name first, matches only in the
message text last. Delete moves the file to
the trash with the `trash` command when there is one, else deletes it, and
refuses a session a live agent shows.

Session details load in the background, so the list fills in while the
title shows `loading`. They are kept by file size and modification time
until Neovim exits; dyadic keeps no database of its own. Opening the picker
also starts loading the All view. Sessions are found as pi finds them:
`--session-dir`, `PI_CODING_AGENT_SESSION_DIR`, project and user
`sessionDir`, and `PI_CODING_AGENT_DIR`, and an active session's directory
comes first.

9. NEOVIM COMMANDS                                           *dyadic-commands*

                                                                     *:Dyadic*
:Dyadic                 Show the last agent, or open one, with the
                        configured placement, and go into its pair
                        (|dyadic-focus|).
:Dyadic new             Open another agent and pi process.
:Dyadic {-pi-args}      Open another agent with pi arguments, such as
                        `-c`, `-r`, or `--model x` (|dyadic-pi-arguments|).
:Dyadic toggle          Inside this tab's pair, hide it and go back to
                        the window used last. Elsewhere, show the pair of
                        this tab's sidebar, or of the last agent with the
                        free placement, and go into it.
:Dyadic agents          Choose among live agents.
:Dyadic composer        Focus the composer, opening it if needed.
:Dyadic {action}        `submit`, `follow_up`, `dequeue`, `abort`, `close`.
:Dyadic review          Show the next undecided hunk (|dyadic-review|).
:Dyadic review {on|off|auto}
                        Review every file, none, or follow the rules, for
                        this agent.
:Dyadic review {accept|reject} [all]
                        Decide the hunk at the cursor, or all of them.
:Dyadic {command}       Any pi command name from |dyadic-pi-commands| but
                        `quit`, such as `model` or `resume`, without
                        touching the draft. Other names, including
                        extension commands, are an error; type those in
                        the composer.

Commands act on the agent of the current buffer, or else the last one used.
`:Dyadic new` and `:Dyadic -r` open another agent; `/new` and `/resume`
change the session inside an existing one, and so do the `new` and `resume`
actions.

                                                        *dyadic-pi-arguments*
When the first argument starts with `-`, `:Dyadic` opens another agent as
`pi` would with these arguments, after `args` from |dyadic-setup|. Words are
split like a shell's: quotes group them, and a leading `~` is the home
directory. Some arguments work differently than in a terminal:

- `-r`, `--resume`: dyadic's session picker (|dyadic-sessions|) shows the
  sessions of Neovim's cwd and opens the one you choose with `--session`.
- `--session {id}`: an ID that only matches another directory's session asks
  whether to fork it into this directory, as pi does, and opens the fork.
- Messages, the words pi does not read as options or their values, and all
  words after `--`, become the new agent's draft instead of being sent:
  `:Dyadic -c -- now fix the test`.
- Arguments that start no agent are refused: `-p`, `--mode`, `--help`,
  `--version`, `--list-models`, `--export`, and `@file`.

A resumed session runs in its own directory (|dyadic-agents|).

11. EDITOR FILES                                                *dyadic-files*

With the bridge (|dyadic-bridge|), pi's `read`, `edit`, and `write` tools go
through the editor; pi keeps its own matching, results, and rendering:

- `read` returns a file's buffer text when the file is loaded with unsaved
  changes, and reads the disk otherwise.
- `edit` and `write` change a loaded file in its buffer, matching against
  the buffer's text, and then save it with a normal |:write|, so save hooks
  such as formatters run and your own unsaved changes are saved too. The
  change lands hunk by hunk, so marks and folds on other lines stay, and one
  |u| undoes it. A file without a buffer is written to disk as by stock pi.
  This applies when the change is not reviewed (below).

The model is told this once, in the tools' guidelines; results stay pi's,
except for what a review decided and change notes (both below).

Other tools, such as `bash`, work on the disk. After a tool other than
`read`, `grep`, `find`, or `ls` finishes, dyadic runs |:checktime| on every
loaded, unmodified file buffer, so they follow the agent's changes.
'autoread' decides whether reloading asks first. Buffers with unsaved
changes are skipped; Neovim warns about them at its next timestamp check.

Without the bridge, pi reads files from disk, so save a buffer before asking
about unsaved changes.

Review                                                        *dyadic-review*

With review on for a file, an agent's `edit` or `write` opens the file in a
listed buffer if needed, without changing any window, and applies the change
there as ordinary edits. Each hunk's added lines are highlighted, with the
changed words stronger, and its removed lines show above them, wrapped like
the window wraps text. The tool call waits until you have decided every
hunk. Reviewed changes are never saved; save when you are ready. Commands
that read from disk, such as tests, do not see them until then, and the
model knows this.

The composer's bar shows `review: N hunks` while hunks are undecided, and
`:Dyadic review` shows the next one. The keys act on the hunk at the cursor:
the cursor is on one of its added lines, or, for a hunk that only removes
lines, on the line below them (the last line when they were at the end).
That hunk shows a banner: `Review 1/3` and the keys that do something
there, so with one undecided hunk left it leaves out accepting all and
moving. Elsewhere the keys change nothing and say so. After a decision the
cursor moves to the next undecided hunk. In the reviewed buffer:

  Key   Name            Action ~
  ]c    `next`            Next undecided hunk
  [c    `prev`            Previous undecided hunk
  ga    `accept`          Accept the hunk at the cursor
  gs    `reject`          Reject it; its old lines come back
  gS    `reject_reason`   Reject it with a reason, which asks the model
                        for a revision
  gA    `accept_all`      Accept every undecided hunk

The keys exist only while the review is open; a buffer-local mapping of your
own on the same key comes back afterwards. A plugin that maps one of them
in the buffer during the review, as LSP and git plugins do when they attach
to a file the review opened, gets it back after the review too; until then
the review takes the key again when you enter the buffer or move in it.
Change or disable them with `review.keys`.

Only the keys decide; editing never does, so it never ends a review. You may
edit inside an undecided hunk in as many steps as you like: its banner then
says `edited`, accept takes your version, and reject puts the old lines
back. Edits next to a hunk, even on the line right beside it, stay out of
it, so reject leaves them alone. After your decisions the model learns what
landed: the whole change, which hunks you rejected and why, and whether you
also edited the file; with change notes on (|dyadic-change-notes|), a diff
of your edits instead.

Rejecting all of a new file's content leaves no buffer behind; windows that
showed it stay and show the file shown before. When the run is aborted
during a review, accepted hunks and undecided ones you edited stay, and the
rest are reverted.

Undo and redo                                            *dyadic-review-undo*
The agent's change is one undo step, and so is each decision, accepts
included. A hunk is decided while its decision is in your undo history, and
undecided otherwise. So |u| after a decision reopens the hunk and |CTRL-R|
makes the decision again, the reason included; |u| after an edit inside a
hunk makes it the agent's version again.
Undoing the agent's change itself ends the review: the model is told you
undid it, and |CTRL-R| no longer brings it back (|:undo| and |g+| still
can). Once a review has ended, undo is ordinary editing and the model is
not told; |u| steps back through your decisions first (undoing an accept
only moves the cursor), then undoes the change. Closing the buffer during
a review drops the change, and the model is told so.

One review per buffer runs at a time; another agent's change to the same
buffer waits, and fails when the buffer changed meanwhile, so the model
reads it again.

Whether a file is reviewed:
>lua
    require("dyadic").setup({ review = true })    -- every file
    require("dyadic").setup({
      review = {
        default = false,
        paths = { ["~/work"] = true, ["~/work/scratch"] = false },
        keys = { reject_reason = "gR" },
      },
    })
<
The nearest rule above a file wins, matching whole path components after
`~` expansion and symlink resolution; relative rule paths are relative to
the agent's cwd. Rules and files are compared by where they really are, so
a rule may name a directory that does not exist yet, and a file reached
through a symlink follows the rules of its target. Without a matching rule,
`default` decides. For one agent, `:Dyadic review on` or `:Dyadic review off`
overrides the rules until `:Dyadic review auto`.

Change notes                                            *dyadic-change-notes*

You can edit any file while an agent works with it, and so can formatters,
other agents, and git. The agent's next `read` sees the current text, but it
does not know to read again. With `change_notes = true`, dyadic remembers the
text the agent last saw of each file it read or changed through its tools,
and tells it what changed since:
- When you start a run, a note lists the files that changed, each with a
  diff of up to 20 changed lines, or only where and how much changed when
  more did. The history shows it as one line, `told the agent: ...`, and |K|
  on it shows the note. Each change is told once.
- During a run, an `edit` or `write` whose file ends up different from what
  the agent's tool produced, because a save formatted it or you edited a
  reviewed hunk, says so in its result with the same kind of diff.
The note says the current version stands. After a move in the tree
(|dyadic-tree|), `/new`, `/resume`, `/fork`, or a session switch, dyadic
forgets what the agent saw until it reads or changes the files again. Files
the agent saw only through other tools, such as `bash`, are not tracked.

12. EXTENSIONS AND PROTOCOL LIMITS                         *dyadic-extensions*

Extension UI requests use native equivalents:

- `select`, `confirm`: |vim.ui.select()|.
- `input`: |vim.ui.input()|.
- `editor`: a floating buffer. In Normal mode `g<CR>` accepts, `q` or <Esc>
  cancels. `<Plug>(DyadicEditorAccept)` and `<Plug>(DyadicEditorCancel)` are
  available there.
- Notifications, keyed status entries (in the footer), string-array widgets
  (above or below the draft), titles, and editor text are applied.

Dialogs are shown one at a time. RPC timeouts and closing an agent cancel
pending dialogs, and a late answer never sends a second response.

JSONL export, deleting or renaming
saved sessions in the picker, custom extension renderers, terminal images,
custom editor components, and terminal theme controls are not available.
Images in messages are shown as text placeholders.

Bridge                                                        *dyadic-bridge*

The bridge is dyadic's own pi extension, `pi/dyadic.ts` in this plugin.
dyadic loads it into each agent with `-e` unless `bridge = false`. It adds
only what pi offers to extensions and not to RPC clients; dyadic draws all
of its UI in Neovim. Features that need it: `/reload`, moving or labeling in
the tree picker (|dyadic-tree|), the editor-backed `read`, `edit`, and
`write` tools (|dyadic-files|), reviews (|dyadic-review|), and change notes
(|dyadic-change-notes|). The bridge registers its own `read`, `edit`, and
`write`; another extension that replaces them wins if pi loads it later.

dyadic sends it commands as `/dyadic <name> [json]` prompts. The `/dyadic`
command is hidden from completion and is not meant to be typed.

When the bridge is requested but pi does not report it, for example with an
older pi or a load error, dyadic warns once and the features above are
unavailable; everything else works as with stock pi. The warning names
pi's stderr log when pi wrote one, which holds its load errors.
